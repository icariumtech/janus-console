# Phase 19-01: DATA_DIRECTORY_GUIDE.md Rewrite

## Goal

Fully rewrite `DATA_DIRECTORY_GUIDE.md` to document the live state of the data directory after Phases 15–18. The current guide documents the old structure and must be replaced entirely.

## Context

After Phases 15–18:
- Ship data lives in `data/campaign/ship/ship.yaml` + `data/campaign/ship/deckplan.yaml`
- Characters are per-entity files in `data/campaign/crew/` and `data/campaign/npcs/`
- Visitable locations are in `data/locations/{slug}/` (flat, not nested in galaxy)
- `data/galaxy/` contains only celestial bodies (written once per campaign)
- Deck maps use `deckplan.yaml` with `decks:` list format everywhere
- Locations self-register into orbit maps via `body_slug` + `orbital:` block

### Task 2: Write the new guide

Rewrite with these sections:

#### 1. Overview

Show the new three-way split with an annotated directory tree:

```
data/
├── campaign/           ← campaign state: ship, crew, NPCs, docs
├── galaxy/             ← celestial bodies ONLY — written once per campaign
├── locations/          ← all visitable places — stations, bases, ships, ruins
└── janus/              ← CHARON AI context
```

#### 2. Discovery Mechanism

Explain how locations appear on maps:
- `data/galaxy/` is written once and rarely touched
- `data/locations/` is scanned at runtime — add a directory, it appears in the game
- Orbit maps are built by merging `orbit_map.yaml` (moons) with locations whose `body_slug` matches

#### 3. File Types Reference

| File | Purpose | Location |
|---|---|---|
| `ship.yaml` | Ship identity + systems + resources | `data/campaign/ship/` |
| `deckplan.yaml` | All decks in one file | `data/campaign/ship/` or `data/locations/{slug}/` |
| `location.yaml` | Location identity + spatial context | `data/locations/{slug}/` or `data/galaxy/` |
| `terminal.yaml` | Comm terminal message log | `data/locations/{slug}/comms/{name}/` |
| `crew/{id}.yaml` | Individual crew member | `data/campaign/crew/` |
| `npcs/{id}.yaml` | Individual NPC | `data/campaign/npcs/` |

No `manifest.yaml` in this table — it no longer exists.

#### 4. Location Self-Registration

Document the `body_slug` + `orbital:` pattern:
- How locations inject into orbit maps automatically
- Required fields: `parent_type`, `body_slug`, `system_slug`
- Optional `orbital:` block for orbit map visualization
- **Warning:** `body_slug` and `system_slug` are free-text — a typo silently prevents the location from appearing. Example: `tau-ceti-E` (capital E) will not match `tau-ceti-e` directory.

#### 5. Ship Section

Document the two ship files:
- `data/campaign/ship/ship.yaml` — complete schema reference
- `data/campaign/ship/deckplan.yaml` — deck format reference

Note: ship data uses the same `deckplan.yaml` format as locations, but lives in `campaign/ship/` not `locations/`.

#### 6. Characters Section

Per-entity file format for crew, NPCs, and monsters:
- One file per character
- File IS the character (no wrapper key)
- `id:` field must match filename slug
- Uniqueness enforced at load time (duplicates logged and skipped)

#### 7. deckplan.yaml Schema Reference

Complete field documentation:
```yaml
# Top level
hull:                      # optional ship/facility hull outline
  polygon: [[x,y], ...]   # list of [x,y] coordinate pairs

decks:                     # required: list of deck entries
  - id: main_deck          # required: unique deck identifier
    name: Main Deck        # required: display name
    level: 1               # required: sort key (1 = lowest deck)
    default: true          # optional: first shown when location loads
    rooms:                 # required: list of room entries
      - id: bridge         # required: unique within deck
        name: BRIDGE       # display name (empty string = corridor, no label rendered)
        type: corridor     # optional: 'corridor' skips label rendering
        rects:             # required: list of grid rectangles
          - { x, y, w, h } # x/y = top-left cell, w/h = width/height in cells
        doors:             # optional: list of door entries
          - wall: north    # north/south/east/west
            position: 3    # cell index along the wall
            type: standard # standard | blast_door | airlock
            status: CLOSED # OPEN | CLOSED | LOCKED
        poi:               # optional: points of interest
          - icon: reactor core
            label: Reactor
```

#### 8. Adding a New Location (Step-by-Step)

The key workflow that proves the design works:

1. Create `data/locations/{slug}/`
2. Write `location.yaml` with `parent_type`, `body_slug`, `system_slug`
3. Add `orbital:` block for orbit map injection
4. Optionally add `deckplan.yaml` for encounter map support
5. Optionally add `comms/{terminal_name}/terminal.yaml`
6. Done — the location appears in the orbit map automatically. No galaxy files touched.

#### 9. Adding a New Deck

Add an entry to the existing `deckplan.yaml` under `decks:`:
- Set `level:` to the next integer
- Add `rooms:` array for the deck
- The data loader sorts by `level:` — no filename ordering needed

#### 10. Naming Conventions

- Slugs: lowercase + hyphens only (e.g., `phoebe-station` not `PhoebeStation`)
- Galaxy slugs: astronomical names (`tau-ceti`, `tau-ceti-e`, `phoebe`)
- Location slugs: facility names (`phoebe`, `somnus`, `patrol-gunboat`)
- Avoid slug collisions: galaxy slugs and location slugs share a namespace in `find_location_by_slug()`
