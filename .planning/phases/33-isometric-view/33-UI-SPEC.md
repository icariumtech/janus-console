## Design System

| Property | Value |

| Preset | not applicable |

This phase is overwhelmingly a **geometry** change (the `isoProjection` function), not a visual-surface change. The only new pixels on screen are one toggle button. All styling below is scoped to that button plus the invariants that keep existing map elements legible when re-projected.

**Focal point / visual hierarchy:** No new focal point — the existing map/SVG remains the visual anchor of the screen. The toggle is a secondary overlay control, matching `RESET VIEW`'s visual weight (same chrome, same size, same overlay-grid tier) — it must not compete with the map itself for attention.

## Layout & Interaction Contract

This section supplements the template to capture Phase-33-specific visual/geometry invariants from `33-CONTEXT.md` (D-01 through D-06), since the change is primarily to a projection function rather than new markup.

### Isometric projection parameters (D-01)
- **True isometric**: 30° foreshortening angle, equal on all three axes — NOT the 26.57° ("2:1") pixel-game dimetric convention.
- Concrete `isoProjection({ unitSize, tilt, rotation })` defaults (Claude's discretion per CONTEXT.md): `tilt: 30` (degrees), `rotation: 45` (degrees) — the standard architectural/engineering-drawing isometric axonometric angle pair, matching the `gridProjection.ts` doc comment's own example (`isoProjection({ unitSize: 40, tilt: 30, rotation: 45 })`). Do not expose these as user-facing controls — they are the single fixed "isometric" style, matching the D-02/Phase-31-D-10 "one fixed baked-in style" philosophy.
- `isoProjection` must satisfy the same `Projection` interface contract as `topDownProjection` (`project`/`unproject` are exact inverses within floating-point epsilon) — this is a functional contract, not a visual one, but the checker/executor should treat any visual "drift" (e.g. click targets not lining up with rendered geometry in iso mode) as a projection-interface bug, not a rendering bug.

### Flat re-projection only (D-02)
- No new wall height/extrusion/shading geometry. Walls, hulls, and detail linework render through the identical SVG-drawing code paths as top-down — only the `x, y` values they receive change. Do not add drop-shadows, gradient "wall face" fills, or any other depth cue not already present in top-down.

### Toggle button placement (D-03, D-04)
- Lives in the **bottom-left cell** of `EncounterMapRenderer`'s existing `encounter-map__overlays` CSS grid (`gridTemplateAreas`, currently `"top-left . top-right" ". . ." "bottom-left . bottom-right"` — bottom-left is empty today).
- `gridArea: 'bottom-left'`, `alignSelf: 'end'`, `justifySelf: 'start'` (mirrors `LegendPanel`'s `bottom-right` positioning, reflected horizontally).
- Renders **unconditionally** (not gated on any state) — unlike `RESET VIEW`, which only appears when the view is panned/zoomed.
- Button only, no keyboard shortcut (D-04) — consistent with every other encounter-map control.
- Both the player (`EncounterView`) and GM (`EncounterMapDisplay`) render their own instance of `EncounterMapRenderer`, so each gets its own toggle and its own local `useState` for projection mode — no shared/synced state, satisfying ISO-02/ISO-03's "independently" requirement with zero new prop plumbing.

### Token/label billboarding (D-05)
- Room labels (text), door icons, POI icons, and token glyphs stay **upright and horizontal** in iso mode — only wall/hull/detail *linework* (the geometric outlines) follow the skewed iso transform.
- Mechanically: these elements' *anchor position* is computed via `view.project()` (so they move to the correct projected location), but the elements themselves are NOT wrapped in any rotation/skew transform derived from the projection — they render the same way a `<text>` or icon `<g>` would under top-down, just at new coordinates.
- This is the same visual grammar as isometric tactics-game unit markers (per CONTEXT.md's own framing) — not a new pattern this project has to invent, just apply consistently.
- **Prerequisite migration** (implementation note carried from D-05, relevant to the visual contract because unmigrated call sites will render in the WRONG position under iso, not just wrong style): token position (~line 658) and vent polyline points (~line 567) currently multiply by `unitSize` directly instead of calling `view.project()`. These must be migrated as part of this phase or tokens/vents will not move when iso is active — this is a visual-correctness blocker for ISO-01, not optional cleanup. The planner should audit for any other direct `unitSize` multiplication in `EncounterMapRenderer.tsx` and layer files (Claude's discretion item in CONTEXT.md) and migrate all found instances.

### Map rotation composition (D-06)
- The existing per-ship authored `mapRotation` (0/90/180/270, applied as an outer SVG `rotate()` transform after projection) continues to apply in iso mode — it is orthogonal authoring metadata, not a projection-mode concern.
- Visual expectation: a ship authored with `mapRotation: 90` should look like "the same iso-projected ship, rotated 90° in the projected plane" — i.e., `rotate()` composes AFTER the projection converts grid→SVG, exactly as it does today for top-down. If visual QA finds the composed result reads as distorted rather than "rotated," that is a Claude's-discretion item for the planner/executor to resolve (CONTEXT.md explicitly leaves the exact composition mechanics open) — but the *intent* ("keep applying `mapRotation` in iso") is locked and must not be silently dropped.
